# B마트 PPC 공통 비즈니스 로직

공통 피킹·패킹 / 재고·입고 / 배송 인계 / 부산 5개 지점 산정

작성 기준일: 2026-10-18 · 문서 버전: 1.0 · 용도: 업무 분석 및 구현 설계안

## 1. 목적과 적용 범위

PPC(Picking & Packing Center)의 입고부터 상품 보관, 주문 수락, 재고 예약, 피킹, 주문별 합류 검수, 패킹, 라이더 인계까지를 하나의 업무 흐름으로 정의한다. 모든 지점은 동일한 업무 규칙과 상태 모델을 사용하고 면적, 가구수, 로케이션 및 가용 인력만 지점 설정으로 관리한다.

여기서 **공통 피킹·패킹**은 상온·냉장·냉동의 작업을 공통 작업 모델로 관리하고, 온도별로 분리 피킹한 상품을 주문 단위로 확인한 뒤 온도 적합한 포장 단위로 연결하는 것을 뜻한다. 여러 온도의 상품을 하나의 보관 공간이나 봉투에 무조건 혼합한다는 뜻이 아니다. 단일 주문 피킹, 여러 주문을 묶는 배치 피킹, 작업자 피킹·패킹 겸무 여부는 목포점 운영 방식 확인 후 설정한다.

첨부 요청문의 마지막 요청인 “공통 피킹패킹 포함 PPC 비즈니스 로직”을 기준으로 작성했다. 물리적 설치를 확정하는 5개 지점 시공 설계서나 실제 랙 배치도는 이 문서의 산출물이 아니다. 확정된 수치가 없는 도면을 완성 도면으로 제시하지 않는다.

### 1.1 근거의 구분

| 구분 | 내용 | 적용 방법 |
|---|---|---|
| 제공 확정 기준 | 첨부 요청문의 면적, 가구수, SKU, 랙 사양, 수요 시나리오 | 그대로 적용 |
| 계산 결과 | 면적 배율, 구역별 비례 면적, 정수 SKU, 가구수 기반 수요 | 공식·반올림 근거와 함께 산출 |
| 조건부 기준 | 주문당 8유닛, 온도별 출고 50%·30%·20% | 목포 원본 확인 전 활성화하지 않음 |
| 업무 설계 제안 | 상태 전이, 스캔, 잠금, 예외 처리, FEFO, API·이벤트 | 기존 확정 규칙으로 사칭하지 않고 구현안으로 제안 |
| 원본 확인 필요 | 33평 용도, 랙 수, 적재 공식, 팔레트·박스, 생산성, 운영시간 | 미입력 상태를 유지하고 관련 산정·승인을 차단 |

작업 폴더와 관련 저장소에서 목포점 MD·설계 이미지를 확보하지 못했다. 따라서 원본의 목차, 잔여 33평 배분, 랙 배열 및 생산성을 검증했다는 주장을 하지 않는다. 미확인 값을 0으로 대체하지 않고 `null / NEEDS_SOURCE`로 관리한다.

관련 배송 연동 근거는 `piaa1004/bmart-delivery`의 기존 DB 예시와 라이더 업무 문서다. 기존 자료는 개발 참고안이며 실제 B마트 내부 운영 기준을 증명하는 자료가 아니다. 이 문서의 업무 로직도 실제 운영 정책과 대조하여 확정해야 한다.

## 2. 공통 기준과 설정 관리

### 2.1 변경하지 않는 물리 기준

| 항목 | 값 |
|---|---:|
| 목포 기준 면적 | 463평 |
| 기준 총 SKU | 10,900개 |
| 상온 / 냉장 / 냉동 SKU 비율 | 50% / 30% / 20% |
| 랙 가로 × 깊이 × 높이 | 1,250 × 450 × 2,100mm |
| 랙 층수 | 6단 |
| 선반당 설계 허용하중 | 150kg |
| 랙 사이 통로 | 700mm |
| SKU 로케이션·바코드 | 기존 체계 유지 |

랙 점유면적은 1.25 × 0.45 = 0.5625㎡이지만 이 면적만 나눠 랙 수를 정하지 않는다. 700mm 통로, 출입·회전, 기둥·설비, 기존 배열을 포함한 실측 좌표 검증이 필요하다. 통로 규격을 임의로 바꾸어 배치 가능 판정을 만들지 않는다.

### 2.2 설정 계층과 승인

`공통 기준 버전 → 지점 설정 버전 → 시나리오 입력 → 계산 스냅샷 → 검증 결과`를 보관한다. 지점은 랙 사양과 수요 계산 공식을 재정의할 수 없다. 모든 변경에는 출처, 변경 전후 값, 작성·승인 주체, 적용일을 기록한다. 실제 SKU의 온도·분류와 재고는 상품 마스터로 결정하며 비율만으로 실상품을 배정하지 않는다.

계산용 `forecast_status`와 설계용 `design_status`, 운영용 `operating_status`를 분리한다. 예측 표가 계산되었다고 랙 배치나 운영 개시가 승인된 것으로 취급하지 않는다.

## 3. 담당자와 권한

| 주체 | 주요 업무 | 제한 |
|---|---|---|
| 고객·주문 서비스 | 주문·취소 요청, 대체 상품 동의, 결제 | 물류 완료 상태 직접 변경 불가 |
| 입고·검수 담당 | 발주 대비 수량·로트·온도·파손 확인 | 부적합 재고를 판매 가능으로 임의 전환 불가 |
| 재고·보충 담당 | 적치, 피킹면 보충, 실사 | 이동 양쪽 위치와 원장 근거 필요 |
| 피커 | 본인 할당 작업, 위치·상품·토트 스캔 | 다른 작업자의 작업을 중복 확정 불가 |
| 패커 | 합류 검수, 봉투·박스 생성, 봉인·보관 | 미검수·취소·보류 주문 출하 불가 |
| 점포 책임자 | 재할당, 차이 승인, 폐기·예외 판단 | 원장 삭제·과거 이력 덮어쓰기 불가 |
| 배송 서비스·라이더 | 배차, 전체 포장물 픽업·인계 확인 | PPC 재고·포장물 명세 임의 수정 불가 |
| 본사 관리자 | 공통 정책·설정 버전·지점 비교 | 확정 기준 변경 시 근거·이력 필수 |

모든 작업은 지점 범위 권한을 확인한다. 점원 화면에는 작업에 필요한 주문·포장 식별 정보를 제공하며 고객 개인정보 노출은 역할별로 제한한다.

## 4. 전체 프로세스

1. 수요 예측과 재고 현황으로 발주 제안 → 발주 승인 → 입고 예정 등록.
2. 수량·유통기한·로트·온도 검수 → 적합 재고 적치 → 판매 가능 재고 반영.
3. 결제·서비스 가능·가용 재고 확인 → 주문 수락 및 재고 예약.
4. 주문을 온도별 피킹 작업으로 분할 → 작업 할당 → 위치·상품·토트 스캔.
5. 주문별 합류 검수 → 상품·수량·품질 재확인 → 온도별 포장 단위 생성.
6. 포장 완료 → 온도 적합한 출하대기 위치에 보관 → 배송 준비 완료 통지.
7. 현재 배차 라이더와 포장물별 인계 확정·해당 재고 출고 → 필수 포장물 전체 완료 확인.
8. 배송 완료·사고·반품 결과 수신 → 별도 반품 검수·정산 처리.

배차 요청은 정책에 따라 포장 시작 시점부터 가능하다. 라이더 도착이나 배차 수락은 포장 완료를 의미하지 않는다. 배차와 포장 상태를 독립적으로 유지하며, 실제 인계 때 두 조건을 모두 검증한다.

## 5. 상태 모델과 핵심 불변식

### 5.1 상태를 업무별로 분리

| 대상 | 정상 상태 흐름 | 예외·종료 |
|---|---|---|
| PPC 이행 | RECEIVED → RESERVED → PICKING → CONSOLIDATING → PACKING → READY_FOR_HANDOVER → PARTIALLY_HANDED_OVER → STORE_HANDOVER_COMPLETED | ON_HOLD, CANCEL_REQUESTED, CANCELLED |
| 온도별 피킹 작업 | PENDING → ASSIGNED → IN_PROGRESS → DONE | SHORT, BLOCKED, CANCELLED |
| 포장물 | DRAFT → VERIFIED → SEALED → STAGED → HANDED_OVER | VOIDED, QUARANTINED |
| 재고 품질 | INSPECTION_PENDING → SELLABLE | BLOCKED, DAMAGED, EXPIRED, DISPOSED |
| 배차 | 배송 시스템의 기존 상태 사용 | PPC 이행 상태와 독립 |

`DONE`은 해당 작업에 승인된 최종 품목·수량이 모두 충족되었을 때만 가능하다. 품절·대체·부분 취소가 있으면 주문 개정 버전과 예약·작업·포장 명세를 함께 갱신한다. 작업 없는 온도 구역은 완료 대상으로 요구하지 않는다.

### 5.2 반드시 유지할 규칙

- 가용 재고는 음수가 될 수 없고, 동일 재고를 두 주문에 중복 예약할 수 없다.
- 주문 품목별 `원주문 수량 = 누적 취소 수량 + 현재 유효 수량`, `현재 유효 수량 = 누적 인계 수량 + 미이행 수량`을 원주문 품목별로 유지한다. 인계 후 회수는 인계 사실을 지우지 않고 별도 회수 원장으로 관리한다. 추가 구매·대체·재배송은 별도 근거와 개정으로 추적한다.
- 피킹된 각 상품은 지점·SKU·로트·위치와 주문 또는 주문별 토트 칸에 연결된다.
- 합류 검수는 최신 주문 개정 버전을 대상으로 한다. 완료된 작업도 이후 취소·변경 시 재검증한다.
- 포장물의 품목별 합계는 인계 대상 주문 명세와 일치한다. 같은 실물 수량이 두 포장물에 중복 계상되지 않는다. 한 주문상품을 여러 포장물로 나눌 때는 합계가 유효 수량을 초과하지 않는다.
- 배송/승인된 출고 묶음의 필수 포장물이 모두 인계되어야 그 배송의 픽업이 완료된다. 모든 유효 출고 묶음이 끝나야 주문의 인계가 완료된다. 일부 실물이 이미 넘어갔다면 해당 포장물의 인계·출고는 유지한다.
- 온도·품질·유통기한 보류는 다른 온도 작업의 완료나 라이더 도착으로 자동 해제되지 않는다.
- 상태 전이와 재고 원장 기록은 같은 트랜잭션에서 확정하고, 취소는 삭제 대신 보상 기록으로 남긴다.
- 단말 스캔과 외부 이벤트가 재전송되어도 동일 물리 작업·출고·환불은 한 번만 반영된다.

## 6. 입고·검수·적치·보충 로직

### 6.1 입고 처리

입고 예정과 발주 품목을 조회하고 공급처·SKU·로트·유통기한·온도·실수량을 스캔한다. `발주수량 / 도착수량 / 검수합격수량 / 반려수량`을 별도로 기록한다. 미도착과 초과 입고는 자동으로 정상 수량에 합치지 않는다.

검수 대기품은 판매 가능 재고에서 제외한다. 합격품만 허용 온도와 가용 용량이 맞는 위치에 적치하고, 적치 완료 시 판매 가능 재고를 증가시킨다. 부적합품은 격리 상태를 유지한다. 온도 범위·잔여 유통기한·검사 기준은 원본 또는 승인 정책을 사용하며 임의 숫자로 채우지 않는다.

### 6.2 피킹면 보충

로트별 판매 가능 수량과 예약 수량, 피킹면 잔량을 확인한다. 원본 보충점·상한이 있으면 재사용하고, 없다면 설정 미완료로 표시한다. 보충은 재고의 위치 이동이며 지점 총재고 증가가 아니다. 출발·도착 위치 스캔과 수량 일치를 원자적으로 기록하고 피킹 중인 동일 재고의 이중 할당을 방지한다.

유통기한 관리 상품은 FEFO(먼저 만료되는 적합 로트 우선)를 제안한다. 유통기한·배송 가능 잔여기간·품질 조건을 만족한 로트만 대상으로 하고, FEFO를 이미 확정된 목포 기준으로 간주하지 않는다. 비유통기한 상품의 우선순위는 원본 정책을 확인한다.

## 7. 주문 수락과 재고 예약

1. 주문 식별자·중복 요청·결제 결과·서비스 지점·판매 상태를 확인한다.
2. 주문 SKU별 판매 가능 재고에서 예약 재고와 기존 안전재고 정책을 제외한 수량을 조회한다. 안전재고가 정의되지 않았다면 자동으로 임의 수량을 차감하지 않는다.
3. 로트·위치별 가용성을 잠금 또는 조건부 갱신으로 확인하고 예약을 생성한다. 다품목 주문의 예약 실패는 전체 롤백하거나 승인된 부분 이행 정책으로 처리한다.
4. 예약 성공 뒤 온도별 작업을 생성한다. 결제 완료 후 예약이 실패한 경우 결제 서비스에 취소·환불 보상 요청을 발행하고 결과를 추적한다.
5. 예약 만료시간은 승인 설정에서 읽는다. 할당·피킹 중 재고를 만료 배치가 일방적으로 해제하지 못하도록 상태와 버전을 재확인한다.

### 7.1 배송 DB와 일치하는 재고 의미

기존 배송 DB 예시는 **라이더 인계 시** `sellable_on_hand`와 `reserved_quantity`를 함께 차감한다. 이 문서도 이 기준을 채택한다. 이때 `sellable_on_hand`는 품질상 판매 가능한 지점 보유분이며, 피킹·포장되어 예약된 수량을 포함한다. 고객이 새로 주문할 수 있는 수량은 `available = sellable_on_hand - reserved_quantity - 승인된 추가 보류분`이다. 이미 품질상 제외된 재고를 추가 보류분으로 중복 차감하지 않는다.

피킹 때는 위치 재고를 `선반 → 토트 → 포장물`로 이동시키고 예약 소유자를 유지한다. 판매용 지점 집계에서 다시 출고 차감하지 않는다. 라이더에게 포장물별 실제 인계 확정 때만 해당 명세 기준으로 두 집계를 감소시킨다. 반품품은 검수 후 재판매 가능 판정 때만 반품 입고로 증가시킨다.

## 8. 공통 피킹 로직

### 8.1 작업 생성과 할당

주문 품목을 상품 온도 기준으로 나누고 `주문 / 온도 / 로케이션 / SKU / 로트 / 요구수량 / 주문개정버전`을 작업에 저장한다. 단일 주문 또는 배치 방식은 목포 원본을 따른다. 배치 피킹을 활성화한다면 주문별 칸 식별이 없는 토트 혼적을 허용하지 않는다.

우선순위는 약속된 준비 시각과 잔여 작업량을 사용하도록 제안한다. 작업자 할당은 해당 지점·온도 작업 권한, 현재 작업량, 온도 적합 장비를 확인한다. 같은 작업은 한 명만 점유하고 이탈·단말 장애 시 책임자 재할당으로 기존 할당 버전을 무효화한다.

### 8.2 스캔 순서

`작업 수락 → 위치 스캔 → SKU·로트 스캔 → 수량 확정 → 토트/주문칸 스캔 → 다음 품목 → 구역 작업 완료`를 사용한다. 기존 바코드와 로케이션 값을 재사용하고 신규 체계를 임의로 교체하지 않는다.

서버는 작업 소유자·버전, 예약된 재고, 유통기한·품질, 과피킹 여부, 토트의 주문·온도 적합성을 확인한다. 성공 시 위치 이동 원장과 피킹 실적을 함께 확정한다. 화면의 버튼 완료만으로 실수량 검증을 대체하지 않는다.

### 8.3 부족·오스캔 처리

실물 부족은 `SHORT`로 기록하고 원장 불일치 조사, 다른 적합 로트 재할당, 보충 가능 여부를 확인한다. 승인 없이 다른 SKU로 대체하지 않는다. 대체를 제안하면 고객 동의와 가격·결제 조정을 주문 서비스가 처리하고 승인된 주문 개정 후 작업을 재생성한다. 미해결 품목은 합류·포장 완료를 차단한다.

오스캔·초과 수량은 확정을 거절한다. 이미 잘못 이동된 수량은 역이동·재검수로 복구하고 재전송 요청을 피킹 실적으로 더하지 않는다. 같은 상품 여러 개를 스캔하는 정상 작업과 통신 재시도는 scan_id·단말 순번으로 구분하며 바코드 값 자체로 중복을 판정하지 않는다. 냉장·냉동 상품은 노출시간과 위치를 기록하며 기준 초과 시 품질 보류한다.

## 9. 주문 합류와 공통 패킹 로직

### 9.1 합류 완료 조건

주문에 필요한 온도 구역의 작업만 모아 최신 주문 명세와 대조한다. 각 토트/칸을 스캔하고 `SKU·로트별 실수량 = 개정 후 이행 대상수량`인지 확인한다. 누락·중복·품질 보류·진행 중 취소가 있으면 패킹을 시작하지 않는다.

합류는 주문 연결과 검수의 완료다. 냉장·냉동 상품을 상온 검수대에 무기한 대기시키는 흐름으로 구현하지 않는다. 온도별 물리적 보관 상태를 유지하면서 주문 단위로 준비 여부를 집계한다.

### 9.2 포장 생성과 검증

1. 패커가 주문과 합류 토트를 스캔해 작업을 점유한다.
2. 온도, 상품의 파손·누수·중량·혼적 적합성, 승인 포장 규칙에 따라 포장물을 생성한다. 봉투 수나 보냉재 수를 주문당 고정값으로 가정하지 않는다.
3. 각 포장물에 `package_id`를 부여하고 `package_items`에 주문상품·수량을 연결하고 로트별 상세는 `package_item_lots` 또는 동등 관계로 확장한다. 로트별 합계와 포장상품 수량을 일치시킨다. 부분 수량 분할 시 모든 포장물 합계를 검증한다.
4. 상품 검수 → 포장재·보냉 요건 확인 → 봉인 → 라벨 → 온도 적합한 대기 위치 스캔을 수행한다.
5. 출고 묶음의 필수 포장물이 검증·봉인·적치되었고 미해결 예외가 없을 때 해당 묶음을 준비 완료로 표시한다. 주문 전체 준비는 모든 유효 묶음의 완료를 집계한다.

내부 VERIFIED/SEALED/STAGED는 세부 작업 상태다. 기존 `packages.packing_status`는 필요한 검수·봉인·온도 적합 적치를 모두 통과했을 때 `READY`로 매핑하고, VOIDED/QUARANTINED 또는 재포장 변경 시 준비 상태를 해제한다. 포장 상태와 인계 custody는 별도 필드로 관리한다.

상품 온도 분리 규칙과 허용 노출시간은 반드시 승인 설정에서 가져온다. 포장 후 주문 품목이 바뀌면 기존 포장 명세를 무효화·재검증하고 준비 완료 이벤트를 개정한다. 라이더앱이 오래된 봉투 목록을 사용하지 못하도록 포장 명세 버전을 전달한다.

### 9.3 피킹·패킹 겸무 인력

겸무 인력은 동일 인력 풀에서 작업시간을 공유한다. 피킹 인원과 패킹 인원을 각각 계산한 뒤 같은 사람을 양쪽의 전일 가동 인원으로 중복 계상하지 않는다. 특정 시간에 피킹과 패킹이 겹치면 작업별 필수 배치와 전체 가용시간을 함께 만족해야 한다.

## 10. 출하대기·배차·라이더 인계

출하대기는 승인된 위치와 온도 조건에서 수행한다. 요청문에서 용도가 밝혀지지 않은 33평을 출하대기 공간으로 자동 지정하지 않는다. 외부 출하대기가 원본에서 확인되면 해당 위치와 온도 유지 방식, 대기 한도를 그대로 연결한다.

정상 단일배송은 주문 전체를 한 출고 묶음으로 취급한다. 승인된 분할배송이 있으면 `delivery_id`와 `delivery_packages` 기준으로 필수 포장물을 집계한다. 한 묶음의 준비·인계 완료를 주문 전체 완료로 올리지 않는다.

인계는 기존 배송 예시의 `packages / package_items / delivery_packages / package_handovers` 개념에 맞춘다. PPC는 준비·포장물 명세의 원천, 배송 서비스는 배차·배송 상태의 원천으로 둔다. 기존 테이블이 있으면 중복 테이블을 새로 만들지 않고 로트·작업 세부정보만 확장한다.

| 인계 검증 | 통과 조건 |
|---|---|
| 주문 | 취소·보류가 아니며 현재 명세 버전 일치 |
| 포장 | 이번 인계 대상이 현재 배송의 필수 포장, READY 및 품질 보류 없음 |
| 라이더 | 현재 유효한 배차의 라이더·assignment_id와 일치 |
| 스캔 | 이번 대상 package_id·내용버전 확인, 다른 주문 봉투·중복 인계 없음 |
| 재고 | 해당 예약과 포장물 원장이 일치하고 출고 미반영 상태 |

실제로 넘긴 포장물마다 소유·보관 주체(custody), 인계 기록, 해당 품목·로트의 재고 차감을 같은 로컬 트랜잭션에서 확정하고 `PackageHandedOver`를 발행한다. 사전 스캔만 한 포장물은 인계로 확정하지 않는다. 일부 인계 후에는 `PARTIALLY_HANDED_OVER`를 유지하고 이미 넘긴 실물을 미인계로 되돌리지 않는다. 한 배송의 마지막 필수 포장물까지 인계되면 배송 서비스가 완료 이벤트를 검증한 뒤 그 배송을 `IN_TRANSIT`로 전이한다. 모든 유효 출고 묶음까지 끝나면 PPC 주문은 `STORE_HANDOVER_COMPLETED`가 된다. 기존 배송의 `HANDED_OVER`는 고객 전달 신고 상태이므로 PPC 출고 상태로 재사용하지 않는다.

서비스별 DB를 분리했다면 실물 인계 사실과 outbox를 먼저 확정하고 재고 서비스가 멱등 출고를 반영한다. 출고 반영 지연·실패를 별도 표시하고 재처리한다. 이때 이미 인계된 실물 상태를 되돌리지 않으며 신규 예약에서 미반영 출고를 고려해 과판매를 방지한다.

## 11. 취소·품절·장애 예외

| 상황 | 처리 | 완료 차단·보상 |
|---|---|---|
| 예약 전 취소 | 주문 종료, 진행 중 예약 시도와 버전 경합 확인 | 결제 서비스 취소 결과 추적 |
| 예약 후 피킹 전 취소 | 작업 무효화와 예약 해제를 원자적으로 확정 | 중복 해제 방지 |
| 피킹·포장 후 취소 | 작업·인계 잠금, 실물 회수·품질 확인 | 미피킹분 예약 해제, 피킹분은 반납·격리 확정까지 잠금 유지 |
| 일부·전체 인계 후 취소 | 인계된 포장물은 배송 중단·회수, 미인계분은 인계 차단·회수 | 재고·포장 상태를 인계 전으로 단순 되돌리지 않음 |
| 부분 품절·부분 취소 | 주문 개정, 예약·작업·포장 재대사 | 금액·환불은 결제 서비스가 멱등 처리 |
| 온도·파손 부적합 | 해당 실물·로트 보류, 대체 가능 재고 재확인 | 예약 소유 재고의 불일치 해소 전 출하 차단 |
| 라이더 지연·교체 | 온도 적합 보관, 현재 assignment 재확인 | 오래된 배차의 인계 요청 거절 |
| 단말 오프라인 | 스캔 요청을 미확정으로 저장 후 서버 재전송 | 오프라인 화면만으로 최종 출고 확정 금지 |
| 외부 이벤트 실패 | outbox 재발행·수신 inbox 중복 제거 | 상태·재고 이중 반영 금지 |
| 실사 차이 | 차이 원인과 승인 기록 후 조정 원장 | 예약 상품에 영향이 있으면 해당 주문 보류 |

기존 배송 계약에서 인계 후에는 단순 `CANCELLED`로 되돌리지 않고 `STOPPED` 또는 승인된 회수 흐름을 사용한다. 환불 성공과 실물 재입고는 별도로 관리한다.

취소와 인계가 동시에 요청되면 같은 주문 버전·잠금을 경합하게 한다. 포장물 인계가 먼저 확정되면 해당 실물에 배송 회수 흐름을 적용하고, 취소가 먼저 확정되면 인계를 거절한다. 품질상 판매 불가로 전환하는 피킹 상품은 대응 예약과 지점 집계를 같은 처리에서 정리해 가용 수량이 부풀거나 음수가 되지 않도록 한다.

## 12. 면적·랙·SKU·적재 계산 규칙

### 12.1 면적

`배율 = 지점 면적 / 463`, `구역별 원시 면적 = 목포 구역 면적 × 배율`이다. 제공된 평수는 설계 가능 면적으로 가정하고 목포 전용 463평과 동일한 비교 기준으로 사용한다. 실제 전용면적과 임대면적 차이는 별도 확인 사항이다.

목포의 확인된 구역 합계는 430평이다. 남은 33평은 **배분 미확인 잔여**로 보존하며 새 물리 구역을 생성하지 않는다. 소수 둘째 자리 반올림 차이는 이 잔여행에서만 보정한다. 원본을 확보하면 잔여행을 원래 공간들로 분해하고 동일 비율로 재계산한다. 그 전에는 물리 설계를 승인하지 않는다.

| 구역(평) | 동래점 | 해운대점 | 사하점 | 남구점 | 부산진구점 |
|---|---|---|---|---|---|
| 상온 | 87.73 | 77.21 | 30.55 | 56.67 | 46.61 |
| 냉장 | 134.97 | 118.79 | 47.00 | 87.19 | 71.71 |
| 냉동 | 147.11 | 129.48 | 51.23 | 95.04 | 78.16 |
| 입고검수 | 29.69 | 26.13 | 10.34 | 19.18 | 15.78 |
| 입고창고 | 74.23 | 65.33 | 25.85 | 47.96 | 39.44 |
| 패킹 | 32.39 | 28.51 | 11.28 | 20.93 | 17.21 |
| 공용통로 | 74.23 | 65.33 | 25.85 | 47.96 | 39.44 |
| 배분 미확인 잔여 | 44.55 | 39.22 | 15.50 | 28.77 | 23.65 |
| 합계 | 624.90 | 550.00 | 217.60 | 403.70 | 332.00 |

반올림 보정량: 동래점 +0.01평, 해운대점 +0.02평, 사하점 -0.01평, 남구점 +0.00평, 부산진구점 -0.01평. 이는 미보정 `33 × 배율`을 0.01평으로 반올림한 값에 대한 차이다. 원시 비율은 보존되며 표시값에만 차이가 있다.

### 12.2 SKU

`총 SKU = ROUND_HALF_UP(10,900 × 배율)` 후 50%·30%·20%를 곱한다. 각 온도의 소수부를 내림하고 남는 SKU를 소수부가 큰 순서로 1개씩 배분한다. 동률은 상온→냉장→냉동 순서로 처리한다. 이 최대잔여법은 정수 합계를 맞추기 위한 계산 정책이며 비율의 정수화 오차를 기록한다.

| 지점 | 총 SKU | 상온 | 냉장 | 냉동 |
|---|---|---|---|---|
| 동래점 | 14,711 | 7,356 | 4,413 | 2,942 |
| 해운대점 | 12,948 | 6,474 | 3,884 | 2,590 |
| 사하점 | 5,123 | 2,561 | 1,537 | 1,025 |

SKU는 상품 종류 수이며 재고 유닛 수가 아니다. 면적에 따라 SKU를 비례 조정하는 가상 설계 가정이며 실제 취급 구색이 반드시 면적에 비례하는 것은 아니다.

### 12.3 랙·적재 승인 조건

목포 온도별 랙 수 `R_M,z`가 확보되면 `R_raw,z = R_M,z × 배율`을 구하고 기존 배열을 보존하는 정수 후보를 만든다. 정수화 방식은 원본 배열·실측 형상으로 결정한다. 단순 면적만으로 정수를 확정하지 않는다.

각 후보는 랙 좌표와 실제 외곽선·장애물·출입문을 대조하여 겹침, 경계 이탈, 고정 700mm 통로 누락을 검증한다. 통과한 설치 수 `R_z`에 대해 `선반 수 = 6 × ΣR_z`를 계산한다. 현재 랙 수와 배치 검증은 전 지점 `NEEDS_SOURCE`다.

적재량은 기존 슬롯 수·슬롯 크기·상품 부피·중량·적층·적재율·유효 선반 치수를 재사용한다. 선반의 실제 상품 하중 합계는 150kg 이하를 확인하되, 150kg을 평균 재고 하중으로 간주하지 않는다. `전체 유닛 = Σ선반·슬롯별 허용 유닛`이며 SKU당 평균 슬롯은 `총 사용가능 슬롯 / 총 SKU`로 계산한다. 슬롯 수를 선반 수나 SKU 수와 같다고 가정하지 않는다.

입고창고는 원본 팔레트 규격, 허용 단수, 동선, 온도 및 체류시간으로 계산한다. 면적만으로 팔레트 수·저장 유닛을 확정하지 않는다.

## 14. 발주·입고·박스·팔레트 산정

기존 목포 발주·입고 공식을 먼저 확인한다. 아래는 재고·보충 로직의 구현 틀이며 미확인 주기·안전재고를 임의로 확정한 새 운영 기준이 아니다.

SKU별 수요 예측과 입고 리드타임·검토 주기가 확인되면 목표 재고를 산출하고, `재고 포지션 = 사용 가능 실재고 + 확정 입고 예정 - 미이행 확정 수요`로 계산한다. 사용 가능 실재고가 이미 예약분을 제외한 가용 재고라면 같은 예약 수요를 또 차감하지 않는다. 과거 주문의 예약 수요와 미래 예측 수요의 대상 기간도 겹치지 않도록 한다.

`발주 제안 = max(0, 목표 재고 - 재고 포지션)`을 원본 MOQ·발주배수로 보정하고 공간·유통기한을 검증한다. 미확인 목표재고·리드타임·주기는 `NEEDS_SOURCE`로 반환한다. 일 출고량을 그대로 매일의 입고량이라고 가정하지 않는다.

박스는 SKU별 포장단위로 환산한다. 온전한 박스만 허용되는 발주는 `ceil(SKU 발주 유닛 / 해당 SKU 박스입수)`를 사용한다. 낱개·혼합·부분 박스 허용 여부는 기존 정책에 따른다. 팔레트는 박스별 치수·중량·적층·혼적·온도·기존 팔레트 규격으로 계산한다. 서로 다른 SKU를 단일 평균 입수나 평균 팔레트 계수로 임의 환산하지 않는다.

## 15. 인력·패킹대·처리능력

### 15.1 작업량에 따른 산정

작업 `k`의 일일 업무량을 `W_k`, 확인된 1인 생산성을 `P_k(업무단위/시간)`, 1인 가용 작업시간을 `H_k(시간/일)`로 둔다. `필요 작업시간 = W_k / P_k`, `독립 배치 인원 = ceil(W_k / (P_k × H_k))`다. 생산성에 이미 휴식·손실이 반영되어 있으면 이용률을 다시 곱하지 않는다.

| 작업 | 산정 업무량 예시 | 필요한 원본 입력 |
|---|---|---|
| 입고 하역·적치 | 실제 입고 박스·팔레트·유닛 | 작업 단위별 생산성·입고 시간대 |
| 검수 | 검수 대상 라인·유닛 또는 표본 수 | 검수 방식·대상별 생산성 |
| 피킹 | 온도별 피킹 유닛·라인 | 동일 단위 생산성·이동 포함 범위 |
| 합류·패킹 | 주문·포장물·유닛 | 포함 공정 범위·포장물 구성·생산성 |
| 인계 | 실제 인계 건·포장물 | 건별 확인 시간·라이더 도착 패턴 |

피킹·패킹 공통 인력 풀은 `ceil((W_pick/P_pick + W_pack/P_pack + 겸무에 포함된 부대 작업시간) / 1인 가용시간)`을 일일 작업시간의 하한으로 산출한다. 이어 온도 작업 권한, 휴게, 동시 작업·교대, 시간대별 최소 배치 조건을 만족하는 근무표로 검증한다. 일평균 인원 산식만으로 피크 대응이 보장되지 않는다.

### 15.2 패킹대와 병목

`필요 패킹대 = ceil(피크 시간당 패킹 업무량 / 대당 시간당 처리능력)`이며 대당 처리능력은 실제 배치 인원, 설비, 포장 유형과 공정 포함 범위를 반영한 원본 값을 사용한다. 패킹 구역 면적과 승인 대 규격·작업 동선으로 설치 가능한 대수도 별도 검증한다.

`유닛/시간` 능력을 주문 능력으로 바꾸려면 확인된 유닛/주문이, `포장물/시간`이면 포장물/주문이 필요하다. 모든 단계를 동일한 주문 단위와 기간으로 환산한 후 병목을 비교한다. 단계들이 독립 인력을 사용할 때 `최대 주문 능력 = min(입고·보충, 피킹, 패킹, 인계의 주문 환산 능력)`을 적용할 수 있다. 공통 인력이면 합산 작업시간 제약도 함께 풀어야 하며 단계별 최대치를 동시에 실현할 수 있다고 가정하지 않는다.

지점의 일평균 수요와 피크 수요를 능력과 각각 비교한다. 모든 필수 입력과 검증이 있으면 `ADEQUATE`, 초과가 확인되면 `SHORTAGE`, 입력이 부족하면 `UNKNOWN`으로 표시한다. 부족한 경우 인력·발주 시간대·처리 가능 주문 수를 운영 정책으로 조정하되 원본 고정 사양이나 계산값을 변경해 부족을 숨기지 않는다.

목포 대비 면적당 수요 강도 `(지점가구수 / 75,275) / 면적배율`은 동래점 1.79배 / 해운대점 0.92배 / 사하점 3.66배 / 남구점 2.13배 / 부산진구점 3.81배다. 부산진구·사하의 처리능력 검증을 우선할 수 있지만 이 지수만으로 용량 부족을 확정할 수 없다.

## 17. API·이벤트 계약 제안

아래 경로는 신규 구현 예시이며 기존 API의 실제 경로라고 주장하지 않는다. 모든 변경 API는 지점·역할·현재 상태·version을 검증하고 `Idempotency-Key`를 받는다. 키 범위는 요청자·명령 종류로 구분하며 동일 키에 다른 본문이 오면 충돌로 거절한다.

| 명령 API 예시 | 주요 입력 | 성공 결과·이벤트 |
|---|---|---|
| POST /ppc/fulfillments | order_id, order_revision, branch_id | 예약·작업 생성 / InventoryReserved |
| POST /ppc/pick-tasks/{id}/claim | worker_id, expected_version | 담당자 확정 / PickTaskAssigned |
| POST /ppc/pick-tasks/{id}/scans | scan_id, 위치, SKU·로트, 수량, 토트/칸 | 이동·실적 / PickConfirmed |
| POST /ppc/orders/{id}/consolidate | order_revision, 토트 목록 | 합류 검수 / ConsolidationCompleted |
| POST /ppc/orders/{id}/packages | 주문버전, 포장물별 명세 | package_id 목록 / PackageCreated |
| POST /ppc/packages/{id}/seal | 명세버전, 검수·보관위치 | 검증·봉인 / PackageSealed |
| POST /ppc/deliveries/{id}/packages/{packageId}/handover | delivery_id, assignment_id, package_id, manifest_version, 인계스캔 | 포장물별 인계·출고 / PackageHandedOver |
| POST /ppc/orders/{id}/cancel | 이유, 대상품목, expected_version | 즉시 취소 또는 회수 대기 / CancellationRequested |

이벤트 공통 항목은 `event_id, event_type, occurred_at, branch_id, aggregate_id, aggregate_version, correlation_id, source, payload`다. `PpcReadyForHandover`에는 order_id·delivery_id·order_revision·manifest_version·해당 묶음 필수 package_id·온도별 포장 수·보관 상태를 담는다. `PackageHandedOver`에는 delivery_id·assignment_id·라이더·해당 package_id·인계시각·출고 원장 참조를 담고, 전체 필수 포장물 완료 시 별도 완료 이벤트를 발행한다. 수신자는 event_id 중복과 오래된 aggregate_version을 확인한다.

오류를 `409 STATE_OR_VERSION_CONFLICT`, `422 INVENTORY_OR_MANIFEST_MISMATCH`, `423 QUALITY_OR_CANCELLATION_HOLD`처럼 구분할 수 있다. 실패 응답에는 재시도 가능 여부와 충돌 버전을 포함하고 실물 확인이 필요한 오류를 자동 재시도로 숨기지 않는다.

```text
  save_outbox()
  commit
```

## 19. 검증·운영 지표·도입 순서

### 19.1 인수 검증 시나리오

| 검증 | 기대 결과 |
|---|---|
| 두 주문이 마지막 1개 동시 예약 | 한 주문만 성공, 가용 수량 음수 없음 |
| 같은 피킹 스캔 재전송 | 실적·위치 이동 1회 |
| 배치 토트의 다른 주문 칸 스캔 | 확정 거절 |
| 냉동 작업 미완료 상태에서 패킹 완료 | 완료 거절, 미완료 원인 표시 |
| 부분 취소 후 이전 주문버전으로 봉인 | 충돌 거절 후 명세 재검증 |
| 봉투 3개 중 2개만 실제 인계한 시험 데이터 | 2개만 출고, 잔여 1개는 미인계, 전체 배송 IN_TRANSIT 전이 불가 |
| 배차 교체 후 이전 라이더 인계 | 거절 |
| 취소와 인계 동시 실행 | 한 경로만 확정, 다른 경로 보상 |
| 인계 이벤트 중복·역순 수신 | 출고 1회, 오래된 상태 복귀 없음 |
| 취소된 냉장 피킹품 반납 | 품질 확인 전 새 주문에 재할당 불가 |
| 면적·SKU 합계 | 지점 총면적 및 총 SKU와 정확히 일치 |
| 원본 생산성 누락 | 필요 인원 0명 대신 NEEDS_SOURCE 반환 |

봉투 3개는 로직 시험용 사례이며 주문당 포장 수 기준이 아니다. 업무 검증은 구현 시 수행할 인수 조건이다. 이 산출물에서는 수치 계산·파일 구조·문서 변환을 검증했으며 운영 시스템이 구현·검증 완료되었다는 뜻은 아니다.

### 19.2 운영 지표

주문 수락→준비 완료, 피킹·합류 대기·패킹 소요시간, 피킹 정확도, 품절·대체율, 주문당 포장물 수, 온도 보류 건수, 재고 정확도, 포장 누락·중복, 인계 지연, 시간대별 작업 부하를 측정한다. 목표값은 원본·현장 관측 또는 승인 정책으로 정하며 임의 SLA를 제시하지 않는다.

### 19.3 도입 순서와 미확정 입력

1. 기존 SKU·위치·배송 상태·재고 필드 의미를 대조하고 공통 설정 버전을 확정한다.
2. 예약·원장·단일 주문 온도별 피킹·합류·포장물 전체 인계를 먼저 구현한다.
3. 취소 경합·품절·온도 보류·중복 이벤트·단말 복구를 검증한다.
4. 원본 생산성·입고 주기·시간대별 수요를 확보해 인력·발주·능력 계산을 활성화한다.
5. 원본 운영 방식과 맞는 경우 배치 피킹·공통 인력 배치를 확장하고 현장 실적으로 검증한다.

| 미확정 입력 묶음 | 확정 전 제한 |
|---|---|
| 목포 MD·이미지, 잔여 33평 공간 | 원본 목차 복원·출하대기 면적·물리 도면 승인 보류 |
| 온도별 랙 수·배열·실측 형상 | 설치 랙 수·실제 배치 가능성 산정 보류 |
| 슬롯·상품 부피/중량·적층·적재율 | 유닛 용량·재고 적정성 산정 보류 |
| 입수·팔레트·리드타임·보충 주기 | 발주·입고·박스·팔레트 확정 산정 보류 |
| 8유닛/주문·출고 온도 비중 | 예측 일 출고·온도별 물량 수치 보류 |
| 작업 생산성·시간·교대·패킹대 규격 | 인원·대수·최대 주문·병목 확정 보류 |
| 온도·노출시간·검수·취소·대체 정책 | 해당 예외를 자동 승인하지 않고 담당자 확인 |
